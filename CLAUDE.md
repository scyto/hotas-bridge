# HOTAS Bridge: notes for Claude

Windows app (.NET 8 WinForms + Vortice.DirectInput) that maps HOTAS inputs into games' own binding files. Started with Ace Combat 7.

## Build / run
- `build.cmd` or `dotnet publish HotasBridge.csproj -c Release -o out` (Windows only; DirectInput).
- Bindings persist in `%APPDATA%\HotasBridge\<game>.json`.

## Architecture
- `src/DirectInputService.cs`: enumerates GameControl devices, polls state, and reads **buffered** data so short button pulses are caught (e.g. a thumb wheel in buttons mode).
- `src/Models.cs`: neutral `InputRef` (Axis idx 0–7 = X Y Z Rx Ry Rz Slider0 Slider1 · Button idx · Pov idx+dir) and `GameProfile`.
- `src/IGameAdapter.cs`: per-game contract (config path, actions, syntax, install/backup/restore, `Differences` = what Install would change, compared by value). Register in `GameRegistry.All`. `GameAction.Gesture` is the movement Detect asks for, and `GestureNegative` says whether the game wants it to read as falling values; Detect sets Invert from the two. It only accepts axes for axis actions (throttle detent buttons would otherwise win) and buttons/hats for button actions.
- `src/SystemButtons.cs`: buttons the app acts on itself while it runs, in every game: Guide → Win+G (Xbox Game Bar); Share → tap Win+Alt+PrtScn (screenshot), hold ≥600 ms Win+Alt+G (save clip). They show as the System tab, are stored in `AppSettings.System` (keyed by action key) rather than the game profile, never reach a game file, and may use any button (the app reads DirectInput itself, so AC7's 32-button limit doesn't apply). `Tick` fires them before `CheckListen`, and not while Detect is listening. Confirmed: Guide opens Game Bar. The Game Bar can't be navigated with a DirectInput stick (it takes Xbox controller, mouse or keyboard), so while it's open `MainForm.DriveGameBar` turns actions with a `GameAction.Nav` role (AC7's UI_* menu actions) into keys. Measured: Left/Right arrows move along the widget bar (each widget opens as you land on it, like a pad), Esc closes it, but inside a widget the arrow keys don't move focus (the user hit this), so Up/Down send Shift+Tab/Tab (user-confirmed), Left/Right and LB/RB send arrows, A Enter, B Ctrl+Tab (steps out of a widget to the widget bar; found by the user). Not Esc for B: Esc closes the whole Game Bar, and the Flightdeck pinkie lever (Rz) presses Button10 = UI_B partway through its pull, so it closed by accident. Guide closes it. The Game Bar ignores InputInjector virtual gamepads (tested: WGI saw the pad, focus didn't move, B didn't close). Directions repeat while held.
- `DeviceInfo.IsXInput` (name contains XINPUT/Xbox): Xbox pads show up in DirectInput as type Gamepad, but games read them via XInput, so their card says there's nothing to set up instead of suggesting a type change.
- `src/GameBarState.cs`: is the Game Bar open? `Windows.Gaming.UI.GameBar.IsInputRedirected` is true while it's open (measured); `Visible` stays false for a desktop app, and the Game Bar's windows are neither foreground nor listed by EnumWindows. Called through `IGameBarStatics` (IID 1DB9A292-CC78-4173-BE45-B61E67283EA7, slot 11) with RoGetActivationFactory, because the Windows SDK projection would add 25 MB to a 2 MB app.
- `src/KeyInput.cs`: SendInput helper (arrows, Win and PrtScn sent as extended keys).
- **While the Game Bar is open, Windows pauses DirectInput for other apps and replays the queued presses when it closes** (measured on the Flightdeck Stick: no DI data for 20 s, then 4 queued Button22 presses at once, which reopened the Game Bar). Raw Input with RIDEV_INPUTSINK keeps arriving (~150 HID reports/s). So `src/RawHidInput.cs` reads buttons and hats from Raw Input (HidP_GetData with the preparsed data; DI button i = HID button usage i+1, checked on all 40 stick buttons; hats in report order), and while the Game Bar is open system buttons and navigation use it; DirectInput system presses are ignored for 1.5 s after it closes.
- Grid: one tab per action group (`GameAction.Group`; AC7 Flight / Menus, then System). Columns Action (description), Device, Control (`ControlNames`: per-device names from the Quick Flight Guide, read-only), Binding, INI file (the game's key, n/a for System), Detect, Invert, Clear; cells are set by column name. Planned: a schematic of the device under the tabs, pointing at the control for each action.
- Lesson (2026-11-12): Detect's refusal note was written into the editable Binding cell; clicking into it and leaving saved the sentence as a raw binding, which Install wrote into Input.ini. Now notes go in the read-only Device cell, the Binding cell is read-only while listening, typed text must pass `IGameAdapter.CheckRaw` (AC7 token grammar; buttons above 32 allowed so the limit can be tested), and Restore reloads the grid from the restored file (`ReadBindings`, round-trip tested: 31/31) after backing up `<game>.json`.
- **Controls view** (`src/ControlsView.cs`, `src/ControlLayouts.cs`; Grid | Controls next to the tabs): device-centric editing of the same bindings through `IControlsHost` (implemented by MainForm). `ControlLayouts` groups known devices' controls as they sit on them (keys B28 / X…Slider2 / H1U) and appends every other reported control (within `Presets.PhysicalButtons` / `PhysicalHats`, minus `PhantomAxes`) under Other controls, so nothing is unreachable. The rows are painted on one scrolling surface with one shared dropdown menu (like the device cards); measured with the real devices, a WinForms control per row (48–53 rows, ~300 native windows) made a tab or device switch take 3–6 s, painted it takes ~13 ms. The menu shows where each action is bound now. A dropdown shows only when exactly one action of the tab is on that control as a plain input; typed text or hat-as-axis bindings using the control, or several actions on it, show read-only ("edit in grid"). Picking replaces only what that control did in the tab; unbound actions are listed at the bottom. Inspired by github.com/Alphonsvds/joystick-mapper's photo layouts (GPL-3.0, product photos: idea only, no code or images); a device picture is the planned next step.
- `src/AppSettings.cs`: app preferences in `%APPDATA%\HotasBridge\settings.json` (text size, system buttons).
- `IGameAdapter.MaxButtons`: buttons the game reads (AC7 32). Device cards with more buttons than that show two labelled groups ("Ace Combat 7 reads these" / "can't read these. System buttons can use them"; greying alone read as unusable); Detect's refusals also show in the listening row. `Theme` fonts are rebuilt by `Theme.SetTextScale`; `MainForm.ApplyFonts` hands them out. Assign new `DataGridViewCellStyle`s rather than setting `.Font` on `DefaultCellStyle`, whose getter can return a temporary copy.
- `src/Ac7Adapter.cs`: AC7 `Input.ini`. Preserves unknown lines, strips managed keys from every joystick section before writing, makes a timestamped `.bak-` backup, and writes atomically with CRLF.
- `src/Presets.cs`: built-in presets keyed by DirectInput product GUID.
- `src/DeviceTypeOverride.cs`: changes the DirectInput type a device reports (Flight, Gamepad, Driving, Head tracker, or back to Original) via its OEMData registry value.

## Hard-won facts
- DirectInput product GUID = `{PIDVID-0000-0000-0000-504944564944}` (last block is ASCII "PIDVID"). AC7 section header = `Joystick-` + that GUID.
  - Flightdeck Stick 10F5:7084, Flightdeck Throttle 10F5:7085, VelocityOne Rudder 10F5:7012.
- AC7 reads X Y Z Rx Ry Rz Slider1-2, POV_[UDLR]1-4, Button1-32, modifiers `:P :N :R :C`, operators `& ! + > <`. **The 32-button limit is confirmed in-game** (2026-11-12: Flight_Flare=Button33 did nothing, and AC7 blanked the value when it rewrote Input.ini on exit). It matches DirectInput's classic joystick format (DIJOYSTATE: 32 buttons, 4 hats, 2 sliders). Ace7Game.exe's strings couldn't show it (names like Button28 are built, not listed). CheckRaw refuses typed buttons above 32.
- **AC7 only enumerates DirectInput types Joystick, Flight and 1stPerson.** `EnableDeviceJoystick/Flight/1stPerson` are the only switches in the exe; there's no gamepad one. The VelocityOne Rudder reports HID usage 0x01/0x05 → DirectInput type **Gamepad** (X, Y toe brakes rest at 0; Z rudder rests at centre; 0 buttons), so out of the box AC7 ignores it. Confirmed in-game: yaw did nothing. The Stick and Throttle report 0x01/0x04 → type 1stPerson. When AC7 ignores a device it keeps our section on save but never fills in its ~44-key template. That's how to tell from the file whether it matched.
- **Fix (confirmed in-game, no driver needed): DirectInput's per-device `OEMData` registry value overrides the device type.** `HKCU\System\CurrentControlSet\Control\MediaProperties\PrivateProperties\Joystick\OEM\VID_xxxx&PID_xxxx`, REG_BINARY = DWORD flags + DWORD button count. Measured: `0x10` (JOY_HWS_ISYOKE) → Flight, `0x20` → Gamepad, `0x40` → Driving, `0x02000000` → Supplemental, none → native. The key is per VID/PID; `…&MI_00` per-interface keys are ignored, so the rudder's vendor-only interface (usage FF01) also becomes a 0-axis "game controller". `DirectInputService` drops devices with no controls. DirectInput re-reads the value on every enumeration, even with the same `IDirectInput8`; games read it at start-up. Implemented in `src/DeviceTypeOverride.cs` (the type button on each device card), with the original value backed up in `%APPDATA%\HotasBridge\oem-backup.json`. `IGameAdapter.UnsupportedDevice` says which types a game ignores, and bindings on those devices are skipped.
- vJoy was the fallback (BrunnerInnovation v2.2.2.0 is the only Win10/11-signed build; ViGEmBus is EOL and only emulates Xbox/DS4 pads). It isn't needed while the OEMData trick works.
- AC7's in-game controls menu only configures the Thrustmaster T.Flight HOTAS One. Everything else is `Input.ini` only.
- AC7 rewrites `Input.ini` when it exits, from what it loaded at startup, in its own layout: every device section gets an empty key for each of its 43 actions (20 `Flight_*`, 23 `UI_*`; the adapter lists all 43). So write with the game closed, and compare values, not text (`Differences`).
- AC7 axis directions are per action, not one rule. Throttle: lower values are faster (the usual DirectInput throttle convention). The Flightdeck Throttle's X *rises* going forward (Detect measured it), so it needs `X:R`; in-game, plain X made pulling back accelerate. Pitch: the Flightdeck Stick's Y *falls* going forward (measured: -1 fully forward) and `Y:R` flies right, so AC7 wants pitch rising going forward, the opposite of the throttle. Roll and yaw: right = rising. Camera axis directions haven't been checked, so they have no gesture.
- **AC7's Flight_HatSwitch* settings are the multiplayer instant radio messages** (confirmed in a match, 2026-11-13): Right opens the radio menu and, with it open, sends the selected message to all; Up/Down move the cursor; Left cancels at any time. They do nothing in single player and AC7 leaves them empty by default. They're the same functions as AC7's keyboard radio keys, so those aren't keyboard-only (Multiplayer tab, named as AC7's keyboard screen names them).
- **Keyboard-only functions** (`IGameAdapter.KeyActions`, Keyboard tab): AC7 functions with no Input.ini key, named as AC7's keyboard screen names them, with its default keys: Camera Control Key (Left Alt) and Highlight Target (F). (The radio message keys are not keyboard-only: the Flight_HatSwitch* settings are those functions.) `MainForm.FireKeyActions` holds the key while the bound button is held, only while AC7's window is in front (foreground process = `ProcessName`), not during Detect or while the Game Bar is open. Bindings are stored in the game profile, any button on any device, never written to the file, and kept across Restore. If the user changes AC7's keyboard keys, these need updating. `KeyInput` now sends scan codes as well as virtual keys.
- **Hats as axes** (confirmed in-game: camera on the stick's hat 1): `Flight_CameraPitch=POV_U1 + POV_D1:R`, `Flight_CameraYaw=POV_R1 + POV_L1:R`. Detect on an axis row accepts a hat push (`MainForm.BindHatAxis`, written via `IGameAdapter.HatAxis`, read back with `ParseHatAxis`): up/down binds the vertical pair, left/right the horizontal; the positive direction is up/right, or down/left when the action's `GestureNegative` (throttle). ⇅ swaps the pair; the Control column shows "Hat n up/down".
- **Community findings** (Steam guides 1981342007 and 2210570616, Steam thread 2569816251290811021; 2026-11-13): the hat can drive the camera through the camera axes, `Flight_CameraPitch=POV_U1 + POV_D1:R` / `Flight_CameraYaw=POV_R1 + POV_L1:R` (CheckRaw accepts these, so they can be typed into the Binding cell); the same key on two lines reportedly works; `:P`/`:N` split an axis into two button-like actions (`UI_LeftStickUp=Y:N`); layers via `!`/`&` (`Flight_Pitch=Y:R ! Button10`; hold-to-camera with `&` untested); one guide leaves Flight_HatSwitch* blank so the hat doesn't send radio messages in multiplayer; controller emulators (x360ce, UCR) cause double input, and vJoy reportedly broke on newer Windows 10; there are no deadzone, sensitivity or curve keys.
- **AC7's fresh Input.ini** (deleted and regenerated, 2026-11-13): the four Enable switches default to True (guides saying to turn them on are out of date), and every device it reads gets a section with all 43 keys empty, in AC7's order (Flight_Gun … Flight_Pause, HatSwitch U/D/L/R, Pitch, Roll, Yaw, Throttle, CameraPitch/Yaw, UI_B, UI_A, UI_X, UI_Y, LB, RB, LT, RT, stick presses, D-pad, left stick, right stick, UI_Menu). No default bindings for non-T.Flight devices, so nothing works until bindings are written.
- **AC7's own Input.ini help text** (kept in the file) documents the syntax: objects `X, Y, Z, Rx, Ry, Rz, Slider[1-2], POV_[U, D, L, R][1-4], Button[1-32]`, values `Object:[P, N, R, C]…` (P positive, N negative, R reverse sign, C convert range ±1 → 0..1), mapping `Value1 [&, !, +, >, <] Value2` (& if Value2≠0, ! if Value2==0, + add, > larger, < smaller). Its `Button[1-32]` is the game documenting the 32-button limit. Camera is the CameraPitch/Yaw axes; AC7 also has a camera-control modifier (keyboard Left Alt; T.Flight "B4 + handle axis") that has no Input.ini key among the 43.
- DirectInput has no semantic buttons (Menu/View/Guide are XInput). AC7's `UI_*` actions are how a DirectInput device gets the Xbox buttons; there's no View or Guide action. In flight, an Xbox pad's View button toggles the radar map (`Flight_Radar`) and Menu pauses (`Flight_Pause`); `Flight_View` is the camera toggle (right-stick click on a pad). Guide is a system button that AC7 never sees, so no binding file can give it one. The Flightdeck Stick preset uses 31/32 (either side of START, 22) as View/Menu and makes 22 the system Guide button and 33 the system Share button. Hangar's stick profile has no button settings, and the stick has no keyboard interface (its USB interfaces are game controller, mouse for the trackpad, and audio), so the stick itself can't send Guide or Win+G. The throttle's touchscreen keys can send up to 5 HID key usages with Ctrl/Shift/Alt/Win modifiers (`FlightdeckTouchScreenButton.Binding*`), so a touchscreen key could send Win+G.
- Flightdeck Throttle in DirectInput: type 1stPerson, 8 axes, 47 buttons, 1 hat. X and Y are the two levers (they move together when linked). Rx/Ry is the thumb mini-stick (Rx = forward/back, Ry = left/right: the reverse of the usual convention, user-confirmed), and Button1 is its click. Also under the thumb: hat 1 ("Thumb (hat 1)") and buttons 2–4; button 18 is fire suppression. On the back: the rear wheel, the two rockers (12/13, 14/15), the 4-way (7–10) and button 11 (all user-confirmed). Slider1 is the rear wheel in analog mode; in digital mode the same wheel is buttons 40/41 instead. Slider2 is the flaps lever (bottom right; both user-confirmed). Z is the upper dial's outer ring and Rz the thumb wheel around the mini-stick (user-confirmed), so all eight axes are identified. Buttons 23–33 are three dials (upper, middle, lower; not pads, as an earlier note had it), each press/left/right: the upper dial's inner knob presses 23 (user-confirmed). Hangar's Dial Response page sets the upper dial's outer ring to Analog Axis (Z; Hangar showed 59% where DirectInput read 38526) or Digital Buttons (24/25, by Hangar's "B23-25" label; not logged yet), and a sensitivity (1–3) for each dial's turn buttons: upper inner 26 (−) / 27 (+), middle 29 / 30 (press 28), lower 32 / 33 (press 31). Buttons 16/17 are flaps up/down: the throttle holds 16 while the flaps lever (Slider2) is at its 65535 end and 17 at its 0 end, like the main levers' end buttons. 5/6 are the thumb lever (three positions, middle does nothing; up = 5 and down = 6, each held while it's there). All user-confirmed. The upper dial's inner knob turns as 26/27 (user-confirmed), and the guide's "outer left/right" are the outer ring in its digital mode. This unit's right lever (Y) rests at +0.76 instead of +1 (calibration or manufacturing, per the user); Hangar's Flightdeck module has a calibration mode only for the stick (`EnterCalibrationMode`), none for the throttle. The stick's thumb wheel has the same two modes (Hangar TrimWheelMode): analog = Slider2, digital = buttons 29/30 (user-confirmed). The levers press buttons by themselves (the guide's "virtual detents"; two watcher logs, 2026-11-13): 35 and 38 pulse for ~20 ms each time the levers pass the centre haptic detent (35 = left lever X, 38 = right lever Y, per the user); the end buttons are held only while a lever is at the very end of its travel. Levers moved one at a time (third log): left lever = 19+34 fully forward, 35 centre, 20+36 fully back; right lever = 37 fully forward, 38 centre, 22+39 fully back. 21 was never seen: this unit's right lever only just reaches the top of its sensor range (it read +0.76 at rest until the user calibrated it in Windows), so 37 flickered there and pushing harder did nothing. Windows calibration (`joy.cpl`) only rescales what the PC sees; the firmware fires these buttons from its own sensor value and Hangar's per-lever "dead zones" (`FlightdeckThrottleSettings`: Left/RightDeadZone1TopPCT 100, DeadZone2MidUp/MidDownPCT 50/50, DeadZone3BottomPCT 0, with enable and haptics flags and LinkDeadZones), which match the measured behaviour: ends only at 100 % / 0 %, and a zero-width centre band, hence the 20 ms pulse. The user then lowered the right lever's top zone in Hangar and pushed the profile: 37 fired, 21 still didn't. So 34–39 are the dead-zone buttons (top / middle / bottom) and 19–22 fixed end stops at the sensor's ends (the guide's max/min); the user then confirmed that each of the three zones moves its button and none moves the end stops. This right lever never reaches the end of its sensor, and the fault is in the throttle's own reading: with both levers in the same physical position Hangar shows 60 % left and 55 % right. Hangar's lever picture labels B20 and B22 next to "REV IDL" boxes at the base (an idle/reverse gate? unconfirmed). No published hardware calibration for the Flightdeck throttle was found (2026-11-13); for the VelocityOne Flight yoke, Turtle Beach support supplies a recalibration tool. Hangar's Flightdeck module has calibration only for the stick. The UI kept missing these (a press shorter than a redraw never showed), so a press now stays lit for 250 ms (`DeviceState.Lit`). The touchscreen is a separate keyboard interface (`mi_02`) sending HID key codes.
- Hangar lists the rudder (`DeviceListJSON.json`, DeviceType "Pedals", boot PID 7011), but no device module or profile is installed for it.
- Chrome's Gamepad API exposes only one hat and can miss short pulses. That's why this app is native rather than web.
- Flightdeck Stick has **33 real buttons** although DirectInput reports 40 (34–40 never fire; `Presets.PhysicalButtons` hides them). The stick also reports a third hat that nothing moves (`Presets.PhysicalHats` = 2) and a "Dial" axis not in the guide (both devices report Dial + Slider, which land on Slider1/Slider2). The stick's thumb wheel is Slider2 and the user found nothing that moves Slider1, so `Presets.PhantomAxes` hides it on the card and in the controls view (the grid and Detect still accept it). AC7 can't read 33, so the preset makes it the System Share button; which physical control it is hasn't been pinned down. Separately, the stick has a **HUD NAV** button by LED #7 that the printed guide and Hangar leave out; it is *not* button 33 (user-confirmed), and whether it reports anything to Windows is unknown.
- **Quick Flight Guide button lists** (VelocityOne Flightdeck, doc 370-6524). Stick: 1 touch-pad push (FIRE), 2 trigger full, 3 thumbstick click, 4–7 D-pad N/E/S/W, 8 thumb-wheel click, 9 shaft, 10 pinkie lever, 11–15 base buttons, 16/17 18/19 20/21 three forward/back toggles, 22, 23/24 gear lever forward/back, 25–27 rotary knob left/right/press, 28 trigger stage 1, 29/30 thumb wheel up/down, 31–33 base buttons (with 22); axes X Y Z Rx Ry Rz Slider, plus mouse X/Y: B1's touch pad moves the Windows pointer when the stick's mouse toggle switch is set (works, but awkward to use, per the user). Throttle: 1 hat click, 2–4, 5/6 left/right, 7–10 N/E/S/W, 11, 12–15 up/down pairs, 16/17 forward/back, 18, 19–22 max/min virtual detents, 23–33 upper/middle/lower dials (press/left/right), 34–39 forward/middle/back virtual detents, 40/41 wheel up/down; axes: two levers, ALT knob, mini-stick X/Y, thumb wheel, flap lever, finger wheel. Real counts: stick 33 (reports 40), throttle 41 (reports 47); see `Presets.PhysicalButtons`.
- Flightdeck Stick controls that never reach Windows (Raw Input watcher on every interface, 2026-11-12): the **HUD NAV** button on the left of the grip, below the 4-way D-pad (by LED #7; not in the guide or Hangar) sends no button, hat, value or mouse report: it's the stick's screen-menu button (manual: **hold 3 s** to open the menu, D-pad to navigate, CHRONO starts/stops/resets the chronometer, hold 3 s to leave; a short press does nothing; the menu also has a Key Bindings page). Context: the stick's screen has a top and a bottom slot (Hangar `PanelElementType`: 0 slider, 1 Rz, 2 Z, 3 chronometer, 255 none), and there are no HUD or NAV pages for it to switch to. Read from the stick (profile 'AC7'): panel style 0, top 1 (Rz, the pinkie lever), bottom 3 (chronometer), ProAimButton 0 (off), TrimWheelMode 1 (thumb wheel as buttons 29/30). Hangar's Flightdeck module has no Bluetooth settings; the stick's audio is a wired headset jack over USB. The orange switch left of B1 toggles the touch pad's mouse mode. Pro Aim is not a hidden button: Hangar assigns it to a numbered button (ProAimButton 0 = none, n = Button n). **Buttons 23 and 25 read as held all the time**: switch positions (23 gear lever forward, 25 rotary knob left), so anything watching for presses must use edges, as Detect does.
- Flightdeck Stick (from the Quick Flight Guide): X roll, Y pitch, Z twist, Rx/Ry thumbstick, Rz pinkie lever, Slider2 thumb wheel in analog mode (buttons 29/30 in digital mode, Hangar TrimWheelMode), B1 FIRE pad, B2 trigger full, B28 trigger stage 1, B3 thumbstick click, B4–7 side d-pad N/E/S/W, B8 wheel click, B9 shaft, B10 pinkie, B22 base START, two 8-way hats.
- Turtle Beach VelocityOne Hangar: device and game support are signed .NET plugin packages in its data folder (`Devices\.packages`, `Games\.packages`; manifest with per-file SHA-256 plus a 512-byte `.sig`). Game connectors subclass `TB.Shared.Games.GameInterfaceBase` (IGameInterface, IGameProcessDetection, IActionVariableProvider). Device profiles are unsigned JSON under `Profiles\<device>\`. There's no public SDK.
- Flightdeck stick recovery: hold B3 while plugging in (lights flash blue/green), then Hangar → Stick → Firmware. Throttle: hold B18 while plugging in.

## Hangar device profiles over HID (for loadouts / Fly)
Decoded from Hangar 1.1.1.0's `TB.FlightHangar.Modules.Devices.Flightdeck` 1.2.0.0 (HidSharp) and tested on the real devices, including with Hangar running. Hangar never switches device profiles when a game starts; pushing is manual. Profiles survive unplugging. Profile JSON lives in `<Hangar data>\Profiles\<device>\` (throttle: one subfolder per serial).
- **Stick** (10F5:7084), interface `mi_00`, writes padded to the max output length (1031), 15 ms apart. Push: `[3,65,0]` config (StickAxisProfile, RudderLock, GameVolume, MicVolume, MicMute, AudioEQ, TrimWheelMode, HapticsStrength, (HapticsEnabled<<7)|HapticsZone, ProAimButton, ProAimLevel, TrackPadSensitivity, LEDBrightness, LEDPreset, X/Y/Z deadzone at bytes 3–19; 14 RGB areas from byte 20, area 8 always white; LEDBehaviour at 62), `[3,65,1]` panel (style, upper, lower, name), `[3,65,2]` profile name (ASCII from byte 3). Each is acked `[3,193,pkt]`. Read: `[3,129,0..2]` → `[3,209,0..2]`, same layout. LEDPreset reads back one lower than written.
- **Throttle** (10F5:7085), interface `mi_01` (vendor FF00, 64-byte out reports; Hangar writes 63 bytes starting with 100, replies start `00 B1`). Every packet carries a sequence number at byte 60. Read: `[100,161,6,type,page,button]` for type 3 settings, 4 RGB, 5 name, 1 page (×3), 2 button (×13 per page) → reply `[_,177,type,…]` with the same layout as the push packet. Push (`[100,161,type,…]`, Hangar's order): page and its 13 buttons ×3, settings, RGB, name, then `10`, `6,5`, `6,5`, `10`; each acked `[_,50,209,221,seq]` (or a 177 reply), with `[_,50,FE,FF,seq]` meaning busy, so retry; 15 ms apart, 950 ms after the first `10`. `PageNum` is the profile's page count and the firmware clears pages beyond it. PresetID and LED area 5 don't take; Hangar's own equality check ignores them, along with the button contents. LED colours do take (Commercial's turquoise 40E0D0 read back).
- **Throttle touch can get stuck after profile pushes** (2026-11-12): the screen still showed the pushed profile, but touch did nothing, including on-device page navigation, and the keyboard interface sent no keys (Raw Input watcher). Physical buttons and axes kept working. Unplug/replug fixed it. It was already stuck after our pushes (17:17) and stayed stuck through the user's own Hangar pushes, so it's unknown whether any push causes it (firmware) or ours did. To find out: after a fresh replug, push from Hangar and test touch. The Fly feature must check touch after pushing (or tell the user to replug) until this is understood.
